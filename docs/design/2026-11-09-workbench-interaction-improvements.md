## 1. 目标与实施顺序

本轮解决四个直接影响日常研究流程的问题：编辑的计划与执行版本不一致、重新打开计划后没有实时进度、中小屏三栏相互挤压，以及阅读 PDF 时无法直接继续对话。

| 编号 | 优先级 | 改进项 | 用户可见的完成标准 |
|---|---|---|---|
| UI-01 | P1 | 审阅草稿保护与版本一致性 | 修改后能明确保存、校验和执行同一个版本，未保存内容不会无提示丢失 |
| UI-02 | P1 | 运行中计划自动接续 | 刷新、切回会话或从计划库打开运行中计划，自动恢复进度与控制按钮 |
| UI-03 | P1 | 中小屏响应式工作台 | 打开详情后，聊天、画布和操作区仍可正常使用 |
| UI-04 | P2 | PDF 与聊天并行 | 保持论文可读时完成追问、发送和查看回答，并保留来源与阅读位置 |

建议先完成 UI-01、UI-02，再完成 UI-03，最后基于新的布局规则实施 UI-04。UI-04 的引用草稿与接口设计可提前开展。UI-01 发起 revision 执行后，使用 UI-02 的统一观察流程接续进度。

本轮沿用 React、React Flow、现有 PDF 阅读器和 Aperture 样式体系。证据导航、结果中心、跨运行比较等其他建议不纳入本轮验收。

## 3. UI-01：审阅草稿保护与版本一致性

### 3.1 问题与复现

1. 打开计划审阅，选中一个已保存 revision。
2. 修改节点参数、预算、依赖或名称。
3. 不保存，直接点击“校验”或“批准并运行”。

当前两个动作都使用 `selected` 对应的已保存版本，不会使用尚在 `form` 中的修改。切换 revision、刷新详情或关闭面板，也没有统一的未保存改动保护。

另一个衔接问题是，保存草稿和开始执行目前共用 `onApplied`；主壳中的回调会关闭审阅面板。新增连续操作流程时，应区分保存与执行成功，避免保存后中断审阅。

### 3.2 目标交互

面板常驻显示“正在编辑 rN”以及“已保存 / 有未保存修改 / 保存中 / 保存结果待确认”。执行入口明确标出目标 revision。

| 当前状态 | 校验入口 | 执行入口 | 离开面板或切换版本 |
|---|---|---|---|
| 已保存，未校验 | 校验 rN | 校验通过后允许批准并运行 | 直接离开 |
| 有未保存修改 | 保存并校验 | 先保存并校验，再批准并运行 | 提供“保存后继续 / 放弃修改 / 继续编辑” |
| 保存或校验中 | 显示当前步骤并阻止重复提交 | 禁止执行 | 在当前请求结束前阻止破坏该流程的切换 |
| 校验未通过 | 显示节点与字段错误，允许修改 | 禁止执行 | 有修改时保护草稿 |
| 已校验通过 | 可重新校验 | 批准并运行 rN | 直接离开；修改后校验结果立即失效 |
| 保存结果待确认 | 核对服务端版本 | 禁止审批与执行 | 保留本地内容，先核对服务端状态 |

第一版采用显式“保存并校验”：dirty 时不自动批准，也不以旧版本校验结果解锁运行。保存成功后留在面板，展示新版本号、差异与校验结果；用户随后点击“批准并运行 rN”。

```mermaid
flowchart LR
    A[修改草稿] --> B[保存为新 revision]
    B --> C[校验返回的新 revision]
    C -->|不通过| A
    C -->|通过| D[批准该 revision]
    D --> E[执行同一 revision]
    E --> F[打开运行视图并接续进度]
```

### 3.3 实现要求

- 保存一份经过统一归一化的已加载表单基线；dirty 比较覆盖标题、预算、节点字段、依赖、启用状态和嵌套 inputs。将输入改回原值后应恢复为 clean；输入格式错误不能通过静默转零消除 dirty。
- 区分 `selectedRevision`、服务端实际执行的 `current_revision`、已观察到的 `latest_revision`，以及本地草稿。校验结果绑定具体 revision，不能只保存一个无版本的 `valid` 布尔值。
- 历史 revision 默认只读；“基于此版本创建草稿”是明确操作，展示与最新版本的差异。不能把历史快照无提示覆盖为最新草稿。
- 保存提交显式、正数的 `base_revision`，使用编辑开始时已观察到的最新版本作为并发前提。收到 `revision_conflict` 后保留本地草稿，展示服务端新版本供比较；不能自动换成最新编号并覆盖重试。
- 保存成功后，以响应中的新 revision 编号作为后续读取、校验、审批、执行的唯一目标，不能依赖尚未更新的 React state。
- 拆分“草稿已保存”和“执行已启动”的父层通知。前者更新工作台数据并保留面板，后者关闭审阅并进入 UI-02 的观察流程。
- 使用统一提交锁，流程执行时冻结目标版本与表单；慢请求返回前已切换计划的结果不得覆盖新计划状态。
- 面板内关闭、遮罩关闭、Escape、revision 切换和计划切换统一走离开保护。浏览器刷新使用原生离开提示；桌面窗口关闭需核对实际 bridge 能力，未接入关闭拦截前不能声称已保护系统窗口关闭。

审批和执行仍是两个请求，不能描述为原子操作。审批成功、执行失败时保留“rN 已批准，启动失败”，提供对该版本的启动重试；请求结果不明时先查询计划，避免再次启动。保存请求超时也不能直接重发并假定不会生成重复 revision。

服务端仍是最终判定者：运行中、等待审批或等待输入时的编辑限制，以及 `revision_not_latest`、`plan_running`、`plan_paused` 等响应必须展示明确原因。前端禁用按钮不能替代服务端并发保护。

### 3.4 验收用例

| 编号 | 场景 | 预期 |
|---|---|---|
| R-01 | 修改参数后点击校验 | 先保存新版本，再校验响应中的新编号；不校验旧版本 |
| R-02 | 修改后关闭、切 revision 或切计划 | 可保存、放弃或继续编辑；选择继续编辑时内容完整保留 |
| R-03 | 修改后又恢复原值 | dirty 消失，不出现无意义的离开提示 |
| R-04 | 修改嵌套 inputs 或预算 | 正确识别 dirty；校验结果失效；非法输入定位到字段 |
| R-05 | 另一客户端先保存新版本 | 409 后保留本地修改，不审批、不执行、不自动覆盖 |
| R-06 | 校验未通过或校验请求失败 | 无审批与执行请求；显示错误并保留草稿 |
| R-07 | 快速双击保存或执行 | 每个操作只有一个在途流程，所有后续请求绑定同一版本 |
| R-08 | 审批成功但执行失败或响应丢失 | 不宣称已启动；核对服务端状态后恢复相应操作 |
| R-09 | 保存成功后继续操作 | 面板保持打开，新版本号和基线更新，随后可校验和执行 |

## 4. UI-02：运行中计划自动接续

### 4.1 问题与检查证据

目前刷新或切换会话会读取计划、回填历史；实时连接主要由运行、审批和重试动作建立。切换计划会关闭旧连接，但没有对应的自动观察入口。

模拟打开 `in_progress` 计划时，观察到计划快照和 `/events` 历史请求，未创建 EventSource；页面同时显示“运行中”和“运行计划”。这是“服务端状态”和“本地是否刚执行过”的状态来源分离造成的问题。

### 4.2 状态与按钮规则

业务状态以最新服务端快照为准；连接状态单独呈现为“连接中 / 实时更新 / 正在重连 / 更新已中断”。网络断开不能把业务状态改成失败，也不能重新开放启动按钮。

| 服务端状态 | 是否自动观察 | 主要操作 |
|---|---|---|
| `pending` / `ready` | 未启动时读取快照；本视图启动已受理时立即观察 | 未启动时允许运行；已受理后禁止重复提交 |
| `in_progress` | 自动接续历史与实时事件 | 取消及后端已支持的运行控制；不显示启动操作 |
| `awaiting_approval` | 继续观察 | 处理审批；不重复启动 |
| `awaiting_input` | 继续观察 | 回答问题；不重复启动 |
| `awaiting_review` | 刷新审阅数据；当前视图发起执行后进入观察 | 打开审阅 |
| `paused = true` | 暂停是独立标志，已启动计划仍观察 | 按权限恢复或取消，不通过 execute 绕过暂停 |
| `completed` / `failed` / `canceled` | 回填结果后停止无意义的自动重连 | 查看结果、显式重试或重新运行入口 |

`blocked` 等未列出的状态应按后端实际业务语义补充映射，不能默认显示为“待运行”。`outcome` 是结果质量信息，不作为 SSE 是否结束的唯一依据。

首版自动接续覆盖当前打开的计划，以及当前视图内发起的启动；未订阅的待运行或已结束计划被其他客户端启动时，通过窗口重新聚焦或显式刷新识别，跨客户端即时发现新运行不作为本轮承诺。

执行接口返回 202 后，调度器可能尚未把快照从 `pending` 改为 `in_progress`。因此需要独立的“启动已受理”本地状态：立即建立观察或有限轮询确认启动，不因短暂的 pending 关闭订阅、开放再次运行。确认超时先核对服务端，不把重新 execute 当作查询手段。

### 4.3 统一观察流程

1. 刷新、会话切换、计划库打开、窗口重新聚焦和 revision 执行成功，都进入同一个 `observePlan` 流程；它不调用 execute、retry 或 resume。
2. 读取服务端快照，确认计划可访问，使用新的会话／计划 generation 丢弃旧异步结果。
3. 回填历史事件并获得“已经应用到当前视图”的最高 `seq`；历史与实时事件共用一致的状态归并逻辑。
4. 对需要观察的状态或已确认受理的启动连接 SSE，传递 `after_seq`，由后端回放历史读取后产生的事件并继续实时订阅。
5. 收到有效事件后更新节点与连接状态；关键业务事件刷新快照。收到当前运行的终态后关闭连接，刷新最终结果。

已有 API 使用 `plan_event` 事件名；续接参数是 `after_seq`，不是自造的时间戳。重连沿用现有有限退避，并按当前客户端鉴权策略获取新的短期 ticket，不复用过期 ticket。

### 4.4 一致性与失败边界

- 同一个活动计划在一个工作台实例内只保留一个有效观察流程；React StrictMode、重复聚焦或多次 refresh 不应创建并行的有效订阅。
- 历史回填与实时事件按计划内 `seq` 去重；不能先推进游标、后跳过尚未归并的事件，也不能因历史与实时重叠而重复追加日志。
- 不能假定所有实时事件已有正数 `seq`。当前部分 revision API 在 `AppendEvent` 后发布原事件，可能仍携带 `seq = 0`；本批次应将这类持久化后发布的路径统一为发布带编号的事件。兼容旧事件时，零／缺失 seq 只触发快照或有编号历史的补拉，不推进游标，也不直接重复生成用户通知；心跳不计入业务游标。
- 日志和结果缓存需识别 revision 及可用的执行轮次信息。同一 plan 重新执行时，旧轮次的终态、结果和通知不能结束或覆盖新一轮运行。
- 历史回放只恢复状态，不再次触发“已完成”系统通知、再次执行或审批等副作用。
- 首版可在刷新后重新拉取历史，不强制持久化游标；若持久化，必须连同对应状态快照按用户、计划和运行边界保存。单独恢复游标会漏掉界面尚未还原的内容。
- 切到计划 B 后，关闭计划 A 的连接和重连计时器；A 的历史、ticket 请求和排队回调均不得影响 B。
- `plan_completed`、`plan_failed`、`plan_canceled` 才是现有协议的计划终态事件。等待审批、等待回答和暂停不视为终态。
- 重连次数耗尽时保留最后快照，展示“进度更新已中断”和“重新连接”；不取消服务端任务，不通过重新 execute 恢复观察。
- 401/403/404 停止自动重试并提供对应说明；状态码应通过 ticket 或计划快照请求辨识，不能从不提供 HTTP 状态的原生 EventSource `onerror` 中推断。窗口重新聚焦先核对服务端状态；恢复身份后再显式重建观察流程。

需要抽出“历史归并＋游标”与“观察生命周期”的清晰边界，避免分别在审阅、聊天、计划库等入口复制连接逻辑。前端去重目标是界面状态一致，不承诺网络消息恰好投递一次。

### 4.5 验收用例

| 编号 | 场景 | 预期 |
|---|---|---|
| S-01 | 刷新运行中计划 | 自动建立有效订阅，后续日志和状态实时变化，execute 请求数为 0 |
| S-02 | 切至其他会话再切回 | 自动接续当前计划；旧计划回调不串入当前视图 |
| S-03 | 从计划库打开运行中计划 | 无需点击运行即可看到进度与取消入口 |
| S-04 | 审阅页执行 revision 返回 202，但快照暂为 pending | 关闭审阅后继续观察启动，禁止重复执行，不因 pending 中断订阅 |
| S-05 | 历史读取和 SSE 建立之间产生事件，或收到零 seq 事件 | 有编号事件通过回放补齐，旧零 seq 事件按兼容策略处理，日志不重不漏 |
| S-06 | 断网、ticket 过期、重连次数耗尽 | 有限重试、刷新 ticket、显示中断状态，不把运行改成失败 |
| S-07 | 任务等待审批、等待回答或暂停 | 保持正确业务状态，处理后进度继续更新 |
| S-08 | 完成、失败或取消 | 当前运行终态关闭订阅，错误回调不继续重连，通知不重复 |
| S-09 | 同一计划再次执行、快速切计划、StrictMode | 旧轮次终态不覆盖新运行，没有重复有效订阅 |

## 5. UI-03：中小屏响应式工作台

### 5.1 问题与测量

当前左栏默认占 24%，详情默认 440px，主要布局断点位于 767px。介于手机与宽屏之间的窗口仍保留三栏，缺少各内容区共同的宽度约束。

模拟接口检查数据如下；尺寸是该场景中的实际测量，不代表所有内容都已做视觉验收。

| 窗口 | 详情栏 | 画布内容区宽度 | 现象 |
|---|---|---|---|
| 1366×768 | 打开，440px | 约 465px | 三栏空间紧张 |
| 1024×768 | 打开，440px | 约 205px | 标题、按钮和输入区严重换行 |
| 390×844 | 关闭 | 当前为聊天页 | 左侧内容与底部导航的矩形范围重叠，需纳入遮挡回归 |

### 5.2 布局规则

以工作台实际可用容器宽度计算布局，扣除导航轨、间距、边框和拖动条；不能只依据窗口宽度或百分比。

| 模式 | 初始适用范围 | 布局与详情 |
|---|---|---|
| 宽屏工作台 | 窗口宽度 ≥1280px，且各栏最小宽度可同时满足 | 聊天＋画布，可停靠详情；不足时自动转抽屉 |
| 中屏工作台 | 768–1279px；或宽屏下容器空间不足 | 聊天＋画布，详情覆盖打开；若双栏仍不足则使用单主区切换 |
| 手机工作台 | 窗口宽度 <768px | 对话／执行图单页切换，详情全屏打开并有返回入口 |

初始约束：桌面聊天最小 320px，桌面双栏／三栏中的画布内容区最小 480px，停靠详情最小 360px、默认 440px。最终以全部验收尺寸验证；手机单栏不强制 480px。

三栏可用性按“聊天最小宽度＋画布最小宽度＋详情最小宽度＋容器开销”判定。空间不足时依次限制详情宽度、切为覆盖式详情、收起聊天转为单主区，不能继续缩小文字或把画布挤成窄条。

### 5.3 操作、尺寸与持久化

- 提供可发现的收起／展开聊天入口；收起后保留当前会话、草稿和未发送附件。
- 拖动分隔条时联合约束其他栏的最小宽度；容器缩小后重新计算临时有效宽度，拖动不会产生负宽度或不可恢复的布局。
- 将“用户首选宽度”和“当前有效宽度”分开。临时缩小窗口不覆盖用户宽屏偏好，重新放大后合理恢复。
- 兼容已有 `ra.leftPanelWidth`、`ra.sidebarWidth`；非法或超出范围的缓存值回退并裁剪，旧比例值不能被直接误读为新像素值。
- 中屏详情抽屉提供明确关闭入口、Escape 关闭与关闭后焦点返回。若采用模态遮罩，应完整实现焦点约束与背景不可交互，不能只设置 `aria-modal`。
- 手机主区采用剩余空间分配，避免“标签栏＋100% 高度内容”超过可用高度。底部导航、发送按钮和输入区不得相互覆盖，并处理安全区域、软键盘与横屏。
- 标题可省略并查看完整内容；工具栏合理换行或收起次级操作。运行、取消、关闭、提交回答等主操作不能被裁切。
- 分隔条可通过键盘调整并有明确焦点；手机主要操作点击区域以至少 44×44px 为目标。

### 5.4 验收用例

| 编号 | 场景 | 预期 |
|---|---|---|
| L-01 | 1440×900 与 1366×768 打开详情 | 仅在满足最小宽度时停靠，否则抽屉；画布与输入区可用 |
| L-02 | 1024×768、1024×500 打开详情 | 采用抽屉，关闭后回到原节点，标题和主操作不挤成单字纵列 |
| L-03 | 767/768、1279/1280px 附近连续缩放 | 布局切换稳定；没有负宽度、水平页面溢出或持续跳动 |

## 6. UI-04：PDF 与聊天并行

### 6.1 问题与现有能力边界

`ResearchAssistantApp` 根据 `pdfUrl` 在 `LeftWorkspacePdf` 和 `LeftWorkspaceChat` 之间二选一。PDF 打开后聊天输入框不可见；“询问 AI”仅调用 `setPrompt`，用户需要关闭阅读器才能发送。

划词翻译／解释已通过 `/api/uploads/:id/assist` 获取页码上下文，应保留其直接阅读辅助语义。普通聊天目前的 `ChatRequestOptions` 没有文档引用字段；不能假定把 upload id 写进提示词，就等于后端获得并验证了原文。

此外，`handleSendMessage` 会将有待发送附件的消息判为任务请求。直接把阅读追问的论文加入普通附件列表，会使追问转入计划创建，必须同步处理消息分流。

### 6.2 阅读布局

- 默认研究视图保持“聊天＋执行图”；打开 PDF 后，主区进入“聊天＋论文”的阅读视图。
- 执行图与论文共用主内容区的视图切换，不叠加成“聊天＋论文＋画布＋详情”四栏。切到论文时，已运行计划继续由 UI-02 观察，并保留运行与待办提示。
- 中屏在宽度足够时并排聊天与 PDF，空间不足时提供阅读／对话切换；手机为阅读页与对话页切换，点击“询问 AI”后直接进入可见的对话草稿。
- PDF 工具栏提供“返回执行图”和“显示对话”，无需关闭文档才能发送消息。

### 6.3 来源引用与草稿

将“询问 AI”的参数从裸字符串扩展为引用上下文，至少在前端草稿中保留以下字段：

| 字段 | 用途 |
|---|---|
| `uploadId` | 标识已打开的原文，不使用临时 blob URL 作为文档身份 |
| `documentName` | 引用卡片展示与无效文档提示 |
| `page` | 一基页码；由插件 `pageIndex + 1` 转换 |
| `quote` | 当前选中的原文 |
| `sessionId` | 固定草稿所属会话，防止切换会话后误发送 |

这些是拟新增的前端草稿字段，不表示当前 API 已接受同名字段。

“询问 AI”默认建立可编辑草稿，不立即发送、不自动创建计划；输入框显示“论文名 · 第 N 页”的引用卡片，可返回原页或移除引用。用户已有输入时保留文字，将原文作为独立引用加入，不覆盖原问题。

发送前固定会话、文档、页码和引用快照。切换论文后，已形成的草稿仍指向原论文；切换会话不把原会话引用自动带给新会话。发送失败保留问题与引用，成功后只清理该次已发送草稿。

### 6.4 请求路径与必要接口适配

首版明确区分三类动作：

| 动作 | 路径 | 行为 |
|---|---|---|
| 划词翻译／快速解释 | 现有 document assist | 原地展示结果，不创建计划 |
| 基于原文继续追问 | 普通 chat＋文档引用上下文 | 保留多轮对话；引用本身不触发计划创建 |
| 明确要求复现或执行实验 | 现有 plan 路径 | 经正常任务识别和权限、审阅规则创建计划 |

为普通 chat 增加可选文档引用字段时，应同时修改前端类型、请求序列化、后端 ChatPayload 和上下文装配，而不是只添加 UI 字段。字段命名在实现时与现有上下文模型统一。

后端按当前身份验证 upload 访问权，检查页码范围与引用长度，再读取该页及受预算限制的相邻文本；对扫描、加密、未完成提取等状态返回可解释信息。用户选中文字应作为用户引用保存，不能自动标成服务端已核实的逐字证据。

如果首个交付批次只发送选中文字而未完成上述文档上下文接入，UI 必须准确显示“基于选中文字回答”，且该批次不计为完整 UI-04 验收通过。普通阅读追问和实验任务之间的分流也必须覆盖已有未发送附件的情况。

### 6.5 阅读状态与资源生命周期

- 至少按会话和 upload 保存页码与缩放；来回切换视图、调整宽度、发送消息或查看回答不重置到首页。
- 使用稳定的文档身份管理阅读器；不要因聊天更新、布局切换或组件 key 改变而重建同一 PDF 实例。
- 区分“切回执行图／暂时收起阅读器”和“关闭文档”。前者不清空阅读状态、引用草稿或正在进行的全文翻译任务。
- 关闭文档时释放该文档不再使用的 blob URL、插件回调与订阅；后端翻译任务是否继续需有可见状态，不能把关闭面板等同于已取消服务器任务。
- 打开文档 B 时，文档 A 的慢速下载、元数据和辅助解释响应不能覆盖 B；沿用并补齐 generation 或取消机制。
- 浏览器刷新后的恢复应通过持久 upload 身份重新获取内容，不持久化 blob URL。身份变化或原文无权限时显示恢复失败，不展示其他身份缓存的原文。

### 6.6 验收用例

| 编号 | 场景 | 预期 |
|---|---|---|
| P-01 | 桌面打开论文、选中文字、询问 AI | PDF 保持打开；输入框可见，带论文名和正确的一基页码 |
| P-02 | 输入框已有文字再询问 AI | 原问题保留，引用独立展示并可移除，不自动发送 |
| P-03 | 普通阅读追问后继续多轮对话 | 走 chat，不因引用产生 plan；有待发送附件时也不误分流 |
| P-04 | 发送时切会话或换论文 | 请求仍绑定发送快照，回答落到原会话，不串论文 |
| P-05 | 服务端校验引用 | 越权 upload、越界页码、超长引用和提取失败均有明确响应 |
| P-06 | 阅读／执行图／对话间反复切换 | 页码、缩放、草稿保留，计划继续运行和更新 |
| P-07 | 全文翻译中暂时收起阅读器再打开 | 任务状态可恢复，未重复启动任务，也未被静默取消 |
| P-08 | 390×844、1024×500 阅读追问 | 可进入输入、发送和返回原页；浮层不遮挡关键工具栏 |
| P-09 | 快速换论文、关闭后重开、刷新恢复 | 慢请求不覆盖当前文档；资源正确释放，按 upload 重新恢复 |
